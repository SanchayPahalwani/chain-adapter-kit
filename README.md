# chain-adapter-kit

A reference for how a wallet platform adds a blockchain and moves funds out of it without
sending a withdrawal twice. It makes two claims and tests both. First, adding a chain is
implementing one interface and passing one test suite; the pipeline and the core types do not
change for it. Second, a withdrawal is sent exactly once, even though every step of it can run
more than once. The kit runs against local test chains only (anvil, and Bitcoin Core in
regtest), with test keys only. It is not a custody product, and both adapters refuse to start
against any other network.

## What is in it

- **The interface.** `ChainAdapter` (`src/core/adapter.ts`) is the whole contract for a chain:
  addresses, balances, fee quotes, reserving inputs (a nonce or coins), building a transfer
  and its signing payloads, attaching signatures, broadcast, status, replacement and block
  scanning. Keys stay outside it, behind `Signer`.
- **The conformance suite.** Sixteen checks, C1 to C16 (`src/conformance/suite.ts`), that
  every adapter must pass against its own devnet; `test/<chain>.conformance.test.ts` runs them
  for each chain.
- **Two adapters.** EVM on anvil (`src/adapters/evm/`), for native ETH and an ERC-20 test
  token; Bitcoin on regtest (`src/adapters/bitcoin/`), P2WPKH with replace-by-fee. Each comes
  with devnet controls: fund, mine, drop a transaction from the mempool, reorg.
- **The withdrawal pipeline** (`src/pipeline/`). Requests with an idempotency key; policy
  limits and an address allowlist; M-of-N approvals; a double-entry ledger with idempotent
  postings; workers that claim withdrawals under a lease; every signed transaction stored
  before it is broadcast; re-sending after a drop or a reorg, and replacing a stuck
  transaction; reconciliation of the ledger against on-chain balances.
- **The fault run** (`scripts/fault-run.ts`). On each chain it kills worker processes with
  SIGKILL at every crash point in `src/pipeline/crash.ts` and at random, and injects duplicate
  requests, a dropped transaction, a reorg and a stuck fee. It grades every withdrawal by what
  its destination holds on the chain, then reconciles.

## Quick start

Prerequisites: Docker with Compose, Node 22 or later, and make. The make targets install the
npm packages (`npm ci`) when they need to.

```sh
docker compose up -d --wait   # Postgres, anvil, bitcoind (its image is built locally)
make demo                     # a short tour on EVM, in a schema it drops at the end
make test                     # every test, against the running containers
make faults                   # the fault matrix on both chains; writes docs/results.md
make conformance              # the conformance suite on each chain
make reconcile                # the ledger against the chain, for the schema the env names
```

`make reconcile` reads its schema, seed and chains from the environment. To try it,
`npx tsx scripts/demo.ts --keep` keeps the demo's schema and prints the `export` line that
sets them. `make faults` writes `docs/results.md` only when every scenario passes and the
checkout did not change during the run. `make down` removes the containers and their data.

`docker-compose.yml` publishes every service on 127.0.0.1 only: Postgres on port 55432, anvil
on 58545, bitcoind's RPC on 58443. Its credentials are test-only.

## The signer plug point

`Signer` (`src/core/signer.ts`) has two methods: `publicKey(keyId, curve)` and
`sign(keyId, curve, payload)`. The pipeline passes a key id and the adapter's signing
payloads; it never sees key material. `LocalSigner` (`src/core/local-signer.ts`) is the one
implementation in the repository: it derives test keys from a seed chosen at run time and the
key id, and stores no key anywhere.

An HSM or MPC signer would be another implementation of the same two methods. A worker builds
its signer in one place, `buildRuntime` in `src/pipeline/runtime.ts`, which is where it would
be constructed instead of `LocalSigner`. `docs/design.md` section 7 covers what changes when it
is: latency, repeat signing, a signer that checks the transaction itself, and the signature
format.

## Repository map

```text
src/core/             ChainAdapter, Signer, LocalSigner (test keys), an in-memory InputStore
src/conformance/      the conformance suite and the Devnet controls it uses
src/adapters/evm/     the EVM adapter (viem) and its anvil devnet controls
src/adapters/bitcoin/ the Bitcoin adapter (@scure/btc-signer), its RPC client and devnet controls
src/pipeline/         requests, policy, ledger, worker and its steps, crash points, reconciliation
src/chains.ts         the chain registry: chain name to adapter
src/config.ts         local defaults (127.0.0.1 ports, test-only credentials)
scripts/              demo, fault run, reconcile, migrate, a worker process, chain-cost
scripts/lib/          sandboxes, each chain's test environment, supervisor, scenarios, grading
test/                 unit, conformance, pipeline and fault-run tests
migrations/           the Postgres schema
contracts/            the ERC-20 test token and its compiled ABI and bytecode
docker/bitcoind/      the regtest node image, built from the official Bitcoin Core release
docs/                 design, walkthrough, prior art, adding a chain, results (generated)
```

## What it does not do

From `docs/design.md` section 13, in short:

- Custody of real funds, or key management: no ceremonies, backup or rotation, and no real
  HSM or MPC signer.
- A third chain, and so the after-expiry form of the replacement check (C14).
- A deposit scanner (`scanBlock` exists and passes C15, but nothing consumes it), sweeping,
  UTXO consolidation or batching.
- Cancelling a withdrawal once its nonce or coins are reserved.
- An HTTP API, authentication, users or a UI.
- EVM deposits made by contract-internal transfers, and tokens with unusual behaviour.
- Protection against a reorg deeper than the finality depth, or against someone with write
  access to the database.
- Alerting, operator tooling, or more than one node per chain.
